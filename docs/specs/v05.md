# NBodiesGravity v0.5.0 Implementation Plan

## 1. Release objective

**v0.5.0 is the first formal release produced from the current `feature_v5` branch.**

The objective is not to add a new major feature. The objective is to finish the current feature set, correct the state-management and persistence issues identified during the code review, add regression coverage, clean up documentation, and produce a clean PR:

```text
feature_v5 → main
```

The merge target is **v0.5.0**.

# 4. Step 1 — Fix epoch ownership and consistency

## Problem

The application currently has more than one representation of "where in time the simulation is":

- the actual state of `SolarSystem`;
- the UI's `_last_epoch`;
- the initial epoch used for restart;
- elapsed simulated time.

The known failure mode is:

```text
load date A
   ↓
simulation at A
   ↓
request date B
   ↓
request fails
   ↓
simulation remains at A
but UI epoch bookkeeping can represent B
```

A related issue exists when "New System" reloads J2000 while the previous epoch bookkeeping is retained.

## Goal

There must be exactly one authoritative simulation epoch.

## Recommended implementation

Do not let a requested UI date become authoritative before loading succeeds.

Use a transactional sequence:

```text
requested_epoch
      ↓
fetch data
      ↓
construct new system
      ↓
validate successful load
      ↓
atomically replace active system + epoch
```

On failure:

```text
active system unchanged
active epoch unchanged
UI restored to previous valid epoch
```

## Acceptance criteria

- Loading a valid date changes the active epoch.
- Loading an invalid/unavailable date does not change the active epoch.
- New System resets both simulation and epoch to J2000.
- Restart returns to the actual loaded initial epoch.
- The displayed simulation date always corresponds to the active physical state.

## Tests

Add regression tests for:

1. successful epoch change;
2. failed epoch change;
3. New System after changing date;
4. restart after changing date;
5. elapsed simulation time after restart.

# 5. Step 2 — Make date loading transactional

This is the concrete implementation of the previous requirement.

## Current risk

The date picker state and active simulation state can be changed in different phases.

## Required design

Introduce a distinction between:

```text
requested epoch
active epoch
```

The requested value may change immediately in the UI, but the active epoch changes only after the worker returns a successful complete system.

Conceptually:

```python
requested_epoch = dt

worker.load(requested_epoch)

on_success(system, epoch):
    active_system = system
    active_epoch = epoch
    restart_state = system.clone()

on_error(error):
    restore_date_picker(active_epoch)
```

The exact implementation should follow the existing Qt signal architecture rather than introducing unnecessary global state.

## Acceptance criteria

A failed Horizons request cannot leave any part of the application believing that the failed date is active.

# 7. Step 4 — Complete save/load persistence

## Problem

The current save/load representation stores the main physical parameters but does not preserve every body property that affects the configured simulation/UI behavior.

The body model includes properties such as:

- `label`;
- `active`;
- `show_trail`;
- `show_name`.

These must survive a save/load round trip.

## Required saved information

At minimum, serialize:

```text
name
label
mass
radius
color
position
velocity
active
show_trail
show_name
```

Also preserve the simulation epoch where appropriate.

## Important distinction

A saved system should represent the **current live system**, not automatically the original J2000 state.

The existing usage model already treats Save System as a way to resume from the current state.

## Serialization design

Prefer an explicit schema rather than serializing Python objects directly.

Example conceptual structure:

```json
{
  "format_version": 1,
  "epoch": "2000-01-01T00:00:00",
  "bodies": [
    {
      "name": "Earth",
      "label": "planet",
      "mass": 5.972e24,
      "radius": 6371.0,
      "color": [0.2, 0.4, 1.0],
      "position": [ ... ],
      "velocity": [ ... ],
      "active": true,
      "show_trail": true,
      "show_name": true
    }
  ]
}
```

The exact representation should follow the existing project conventions.

## Tests

Create a round-trip test:

```text
construct system
→ modify every configurable field
→ save
→ load
→ compare
```

Verify all physical and presentation/configuration properties.

# 8. Step 5 — Add persistence schema versioning

Since save files are JSON and the project is beginning formal versioning, the persistence format should be versioned independently.

Use:

```text
format_version
```

inside saved files.

Do not use the application version as the persistence schema version.

Reason:

```text
application v0.5.0
application v0.6.0
```

does not necessarily imply:

```text
save format 5
save format 6
```

A stable `format_version` allows future readers to support older files.

## v0.5 scope

Only establish the mechanism and current schema.

Do not build a complex migration framework yet.

# 9. Step 6 — Resolve the date-loading Cancel behavior

## Problem

The UI exposes a Cancel action for date loading, but the worker does not currently provide complete cancellation semantics.

This creates a mismatch between UI affordance and actual behavior.

## Preferred solution

Implement cancellation if it can be done cleanly within the existing worker architecture.

The worker should:

- expose a cancellation flag;
- check it between body requests;
- stop making additional requests after cancellation;
- report cancellation separately from an error;
- leave the active simulation untouched;
- restore the previous valid epoch.

### Important

Cancellation must not partially replace the active system.

The whole load should remain transactional.

## Alternative

If true cancellation is not worth the complexity for v0.5, remove/disable the misleading Cancel control.

Do not leave a control that appears functional but is not.

## Acceptance criteria

After cancellation:

- the current system remains active;
- the current epoch remains active;
- no partially loaded system is installed;
- the UI returns to a consistent state.

# 10. Step 7 — Fix custom-star classification

## Problem

Rendering currently identifies the Sun specially rather than using the body's semantic classification.

This means a user-created body classified as a star may not receive the same rendering behavior as the Sun.

## Required change

Use the body's classification/label when deciding whether it is rendered as a star/emissive object.

The Sun should naturally be a star because its label says so, rather than because its name is `"Sun"`.

## Acceptance criteria

- Sun renders as a star.
- A custom body labeled `star` renders as a star.
- Renaming the Sun does not accidentally change its physical classification.
- Non-stars with arbitrary names do not render as stars.

## Tests

Add a rendering metadata test around classification.
