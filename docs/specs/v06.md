# NBodiesGravity v0.6.0 Implementation Plan

## 1. Release objective

**v0.6.0 is the numerical robustness and validation release.**

The goal is to move NBodiesGravity from a visually convincing interactive simulator toward a simulator whose numerical behavior can be **measured, bounded, tested and documented**.

The release should not primarily add UI features. It should establish the numerical infrastructure required for later scientific analysis.

The central question for v0.6 is:

> **Can we demonstrate that the simulator behaves correctly and predictably for defined test systems and defined numerical settings?**

---

# 2. Starting point

v0.6 starts from the expected `main` state after the v0.5.0 merge.

v0.5 should have established:

- coherent epoch/state management;
- reliable save/load;
- complete body persistence;
- transactional date loading;
- corrected rendering classification;
- regression coverage;
- formal project versioning.

v0.6 should therefore avoid re-opening v0.5 application-state issues unless a regression is discovered.

---

# 3. Numerical model to document

The current engine uses:

- AU for position;
- AU/day for velocity;
- Solar System Barycentric reference frame;
- Newtonian pairwise gravity;
- Plummer-style gravitational softening;
- Velocity Verlet integration;
- adaptive timestep selection.

The force model is conceptually:

\[
\mathbf{a}_i =
G \sum_{j\neq i}
m_j
\frac{\mathbf{r}_j-\mathbf{r}_i}
{\left(|\mathbf{r}_j-\mathbf{r}_i|^2+\varepsilon^2\right)^{3/2}}
\]

The exact numerical conventions and constants should be documented in the project rather than left implicit in implementation details.

---

# 4. Workstream 1 — Make timestep control explicit

## Current concern

The adaptive timestep is based on the shortest estimated orbital timescale and is bounded by a minimum and maximum value.

The current floor prevents the timestep from becoming zero, but it does not guarantee that a pathological configuration cannot require an impractically large number of substeps.

## Goal

Turn timestep selection into an explicit, testable subsystem.

## Required work

Introduce clear concepts for:

```text
minimum timestep
maximum timestep
maximum substeps per simulation update
orbital-timescale safety factor
```

Keep sensible defaults equivalent to the current behavior where possible.

Do not change defaults without validation.

## Suggested configuration model

Conceptually:

```text
TimeStepConfig
    min_dt
    max_dt
    safety_factor
    max_substeps
```

The exact class structure can follow the existing project style.

## Acceptance criteria

- Timestep selection is deterministic for a given state.
- Minimum and maximum bounds are enforced.
- A pathological system cannot trigger an unbounded integration loop.
- The simulation can report when requested simulation progress cannot be completed within the configured computational budget.

---

# 5. Workstream 2 — Protect against numerical failure

The simulation must detect invalid numerical states.

## Detect

At minimum:

- NaN positions;
- NaN velocities;
- Inf positions;
- Inf velocities;
- invalid accelerations;
- invalid timestep;
- extreme displacement in one integration step;
- body state outside configured physical bounds.

## Behavior

Do not silently continue.

The simulation should:

```text
detect failure
    ↓
stop/pause simulation
    ↓
preserve last valid state
    ↓
expose diagnostic reason
```

The exact UI presentation can be kept simple in v0.6.

## Important

A numerical failure is different from the existing "body beyond 1000 AU" blow-up detection.

The latter is a physical/application boundary.

The former is a numerical-integrity failure.

Keep the concepts separate.

---

# 6. Workstream 3 — Preserve last known valid state

The simulation thread should be able to identify the last valid state.

Conceptually:

```text
state[n] = valid
       ↓
integration
       ↓
state[n+1] = invalid
       ↓
discard state[n+1]
       ↓
pause
       ↓
retain state[n]
```

This should be implemented without allowing the renderer or UI to observe a partially invalid state.

## Tests

Create deterministic tests that deliberately produce invalid states and verify:

- simulation pauses/stops;
- last valid state remains available;
- invalid state is not committed;
- diagnostic information is generated.

---

# 7. Workstream 4 — Add conservation diagnostics

For a closed Newtonian system, calculate:

## Linear momentum

\[
\mathbf P = \sum_i m_i\mathbf v_i
\]

## Center of mass

\[
\mathbf R_{\rm CM} =
\frac{\sum_i m_i\mathbf r_i}
{\sum_i m_i}
\]

## Angular momentum

\[
\mathbf L =
\sum_i
m_i
(\mathbf r_i \times \mathbf v_i)
\]

## Energy

Kinetic:

\[
K =
\frac12
\sum_i m_i|\mathbf v_i|^2
\]

Potential energy must be computed consistently with the project's softened gravitational potential.

The implementation should be careful not to compare a softened force law with an unsoftened potential.

## Output

For each diagnostic quantity, support:

- absolute value;
- initial value;
- current value;
- absolute drift;
- relative drift.

For example:

\[
\Delta E_{\rm rel} =
\frac{E(t)-E(0)}
{|E(0)|}
\]

---

# 8. Workstream 5 — Decide what is a valid numerical tolerance

Do not choose arbitrary tolerances merely to make tests pass.

For each benchmark:

1. establish a reference solution;
2. run with timestep `dt`;
3. run with `dt/2`;
4. run with `dt/4`;
5. measure error;
6. establish a justified tolerance.

This is the beginning of a reproducible numerical validation methodology.

---

# 9. Workstream 6 — Build deterministic benchmark systems

Create a small set of canonical systems.

## Benchmark A — Free particle

One body with no interacting mass.

Expected:

```text
constant velocity
constant acceleration = 0
```

Purpose:

- baseline integrator behavior.

---

## Benchmark B — Two-body circular orbit

Construct an analytically defined two-body system.

Expected:

- approximately constant orbital radius;
- bounded energy error;
- bounded angular momentum error;
- predictable period.

Purpose:

- validate orbital integration independently of real Solar System data.

---

## Benchmark C — Two-body eccentric orbit

Use analytically defined initial conditions producing an eccentric orbit.

Measure:

- periapsis;
- apoapsis;
- period;
- energy drift;
- angular momentum drift.

Purpose:

- validate behavior beyond the easiest circular orbit.

---

## Benchmark D — Earth-Sun

Use controlled initial conditions.

Measure:

- orbital period;
- semi-major axis;
- eccentricity;
- energy drift.

Purpose:

- realistic planetary benchmark.

---

## Benchmark E — Earth-Moon

Use a sufficiently resolved timestep.

Measure:

- lunar period;
- relative Earth-Moon distance;
- stability;
- conservation.

Purpose:

- stress the adaptive timestep because of the short lunar timescale.

---

## Benchmark F — Three-body system

Use a deterministic non-trivial three-body configuration.

Purpose:

- test that the implementation handles genuine N-body coupling rather than only near-two-body systems.

---

# 10. Workstream 7 — Convergence tests

For each canonical benchmark:

```text
dt
dt / 2
dt / 4
```

Compare the resulting state after a fixed physical time.

Measure:

```text
position error
velocity error
energy error
orbital parameter error
```

The exact convergence order should be determined empirically and documented.

Do not assume that the complete adaptive algorithm has the same formal properties as fixed-step Velocity Verlet.

---

# 11. Workstream 8 — Clarify adaptive Velocity Verlet semantics

The current implementation uses Velocity Verlet with a variable timestep.

That distinction should be explicit.

A fixed-step Velocity Verlet method has strong long-term properties associated with symplectic integration.

When the timestep changes according to the system state, those formal properties do not automatically carry over unchanged.

Therefore:

### Documentation should say

The project uses:

> **Velocity Verlet integration with adaptive timestep control.**

Do not make stronger claims about strict symplecticity unless the implementation and analysis justify them.

## Experimental validation

Measure whether adaptive stepping introduces materially different long-term drift compared with fixed-step runs.

This is more useful than making a purely theoretical claim.

---

# 12. Workstream 9 — Softening validation

The current gravitational softening parameter is approximately:

```text
ε = 10^-4 AU
```

This is useful for numerical robustness during close encounters, but it modifies the gravitational potential at short distances.

## v0.6 tasks

Document:

- why softening exists;
- its current value;
- the force law;
- the associated potential;
- where the softened behavior becomes significant.

## Tests

Run a controlled two-body system with several softening values:

```text
ε
ε / 10
ε × 10
```

Measure the effect on:

- orbital radius;
- energy;
- close-approach behavior.

The goal is not necessarily to change the default value.

The goal is to understand and document its effect.

---

# 13. Workstream 10 — Collision/merger numerical behavior

The current collision model is intentionally simplified.

It approximately performs an inelastic merge while conserving:

- total mass;
- linear momentum;
- volume under an equal-density assumption.

However, the merged body's position should be reviewed carefully.

## v0.6 investigation

Evaluate the use of the center-of-mass position:

\[
\mathbf r_{\rm new} =
\frac{m_1\mathbf r_1+m_2\mathbf r_2}
{m_1+m_2}
\]

Determine whether changing to this model is desirable for the supported physical interpretation.

## Also document

The current merger does not model:

- impact energy;
- deformation;
- fragmentation;
- heat;
- angular momentum redistribution.

Do not introduce a complex impact model in v0.6.

The objective is to define and test the current simplified model.

---

# 14. Workstream 11 — Numerical diagnostics API

Create a reusable diagnostics layer independent of the UI.

The UI should not calculate scientific quantities itself.

Conceptually:

```text
Simulation state
       ↓
Diagnostics
       ├── energy
       ├── momentum
       ├── angular momentum
       ├── center of mass
       └── drift metrics
```

This layer will later become the foundation for v0.7's visualization and analysis tools.

---

# 15. Workstream 12 — Regression-test organization

Extend the current test structure rather than creating an unrelated testing framework.

Suggested structure:

```text
tests/
    engine/
    data/
    rendering/
    ui/
    validation/
```

`validation/` should contain deterministic scientific benchmarks.

Keep benchmark definitions small and reproducible.

Avoid tests whose result depends on:

- network access;
- current JPL data;
- wall-clock timing;
- GPU behavior.

External-data validation can exist separately.

---

# 16. Workstream 13 — Long-term stability experiments

After the deterministic tests work, run longer simulations.

Suggested horizons:

```text
Earth-Sun:
    10 years
    100 years
    longer where practical

Earth-Moon:
    shorter but high-resolution runs

Multi-body Solar System:
    progressively longer runs
```

Track:

- energy drift;
- momentum drift;
- angular momentum drift;
- orbital parameter drift;
- adaptive timestep statistics.

The purpose is to establish empirical stability characteristics.

Do not set an arbitrary "must be accurate for 1,000 years" requirement without first measuring the computational cost and scientific meaning.

---

# 17. Workstream 14 — Performance measurements for the numerical loop

v0.6 should establish baseline measurements that v0.8 can later use.

Record:

- bodies simulated;
- physics updates/sec;
- average integration time;
- acceleration calculation time;
- average timestep;
- minimum timestep;
- maximum timestep;
- number of substeps;
- simulation-time advancement per real second.

This can initially be a headless benchmark rather than a polished UI.

---

# 18. Workstream 15 — Numerical logging/reporting

Provide a lightweight diagnostic mechanism for development builds or validation scripts.

Example output:

```text
Benchmark: Earth-Sun
Duration: 10 years
Initial energy: ...
Final energy: ...
Relative energy drift: ...
Initial |P|: ...
Final |P|: ...
Relative angular momentum drift: ...
Average dt: ...
Minimum dt: ...
Maximum dt: ...
Substeps: ...
```

The format should be machine-readable where practical so future automated validation can consume it.

---

# 19. What v0.6 should NOT do

Do not turn v0.6 into a broad feature release.

Explicitly defer:

- major UI redesign;
- orbital plots;
- interactive diagnostics panels;
- GPU acceleration;
- Barnes-Hut;
- large-N architecture;
- advanced collision physics;
- relativistic physics;
- procedural universe generation.

Those should only be considered after the numerical foundation is established.
