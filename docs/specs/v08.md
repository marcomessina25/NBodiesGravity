# NBodiesGravity v0.8.0 — Detailed Implementation Plan

## 1. Release objective

**v0.8.0 is the performance, scalability, diagnostics-usability, and runtime-efficiency release.**

The objective is not to change the physical model. It is to make the existing validated
simulation engine faster, more predictable at larger body counts, and more efficient in
the UI/data-loading path.

The guiding rule for v0.8 is:

> **Measure first, optimize second, validate continuously.**

The current direct vectorized O(N²) Newtonian engine remains the reference implementation.
Do not replace it with Barnes-Hut, GPU acceleration, multiprocessing, or another
approximation merely because those technologies are available. Such changes are only
justified if profiling demonstrates a real bottleneck that cannot be solved adequately
within the current architecture.

v0.8 should also absorb the small v0.7 UI items that are clearly usability/performance
related rather than scientific-model changes:

- diagnostics drift badges;
- diagnostics time-window selection;
- any small plotting throttling/data-decimation improvements demonstrated to be useful.

These should remain secondary to measured performance work.

---

## 2. Baseline

v0.8 starts from the merged and validated v0.7.0 state.

Expected baseline:

- Newtonian pairwise N-body gravity;
- NumPy-vectorized force calculation;
- Velocity Verlet;
- adaptive timestep with explicit limits and substep budget;
- Plummer gravitational softening;
- collision merging;
- numerical-integrity protection;
- conservation diagnostics;
- diagnostics history buffer;
- orbital-element calculations;
- scientific diagnostics UI;
- live plots;
- CSV/JSON diagnostics export;
- deterministic benchmark systems;
- orbital analytical validation;
- long-term stability tests;
- background simulation thread;
- immutable snapshots for rendering;
- JPL Horizons loading/cache;
- JSON persistence.

The v0.7 scientific behavior must remain the correctness baseline.

### Required starting measurements

Before optimization:

1. Run the complete test suite.
2. Run all deterministic benchmark systems.
3. Run the existing benchmark script.
4. Record CPU time, wall-clock time, simulation rate and substeps.
5. Record representative body counts.
6. Record representative timestep configurations.
7. Profile a normal Solar System run.
8. Profile a deliberately larger synthetic system.
9. Record UI frame/update timing.
10. Record Horizons/data-loading timing.

No optimization should be accepted without a before/after measurement.

# 4. Workstream 1 — Profiling infrastructure

## Objective

Create a repeatable way to identify where execution time is actually spent.

### 4.1 Physics profiling

Measure separately:

- acceleration/force calculation;
- adaptive timestep calculation;
- collision detection;
- collision merging;
- integration;
- diagnostics evaluation;
- snapshot construction;
- array copies/conversions.

Do not initially optimize any of these.

### 4.2 Thread profiling

Measure:

- simulation-thread loop time;
- time spent waiting/sleeping;
- simulation work per iteration;
- snapshot publication frequency;
- diagnostics update frequency.

### 4.3 UI profiling

Measure:

- OpenGL render time;
- Qt event-loop responsiveness;
- diagnostics refresh time;
- Matplotlib redraw time;
- plot-history extraction time;
- body-list/orbital-element refresh time.

### 4.4 Data-loading profiling

Measure:

- Horizons request time;
- cache lookup time;
- parsing time;
- construction of body/state objects;
- multi-body loading time.

### Acceptance criteria

A benchmark/profile report must identify the dominant costs before code optimization
starts.

# 5. Workstream 2 — Physics-engine optimization

## Objective

Reduce runtime of the validated O(N²) physics path without changing its numerical model.

## 5.1 Preserve the reference implementation

The optimized implementation must remain mathematically equivalent to the current
Newtonian force model within explicitly tested floating-point tolerances.

Do not change:

- gravitational constant;
- unit conventions;
- softening model;
- collision semantics;
- integrator semantics;
- adaptive timestep policy

unless a separate scientifically justified change is explicitly introduced.

## 5.2 Force-calculation optimization

Profile the current NumPy implementation and identify:

- temporary arrays;
- repeated broadcasting;
- repeated norm calculations;
- unnecessary copies;
- redundant intermediate values.

Potential optimizations may include:

- reusing intermediate arrays;
- improving array layout;
- reducing temporary allocations;
- computing shared pairwise quantities once;
- using in-place operations where safe.

Every optimization must have a correctness test.

## 5.3 Adaptive timestep optimization

Measure the cost of:

- pairwise timescale estimation;
- repeated norm calculations;
- repeated scans of the same state.

Only optimize if profiling shows it is material.

## 5.4 Collision detection

Measure collision detection separately.

Potential optimizations:

- avoid unnecessary allocations;
- reuse distance calculations when mathematically safe;
- short-circuit obvious non-colliding configurations.

Do not alter collision outcomes.

# 6. Workstream 3 — Memory and allocation optimization

## Objective

Reduce allocation pressure, especially for larger N.

Measure:

- peak memory;
- allocations per physics step;
- temporary NumPy array sizes;
- snapshot allocation frequency;
- diagnostics-history copies;
- rendering-side conversions.

### Important rule

Do not optimize by sharing mutable arrays across simulation and rendering threads.

The existing immutable-snapshot boundary is a correctness feature.

Possible safe approaches:

- reuse internal engine scratch buffers;
- reduce temporary allocations;
- copy only at defined ownership boundaries;
- avoid repeated dtype conversions.

### Acceptance criteria

- no mutable simulation array is exposed to the renderer;
- tests continue to pass;
- measured memory allocation decreases where optimization is claimed.

---

# 7. Workstream 4 — Snapshot and simulation-thread optimization

## Objective

Reduce overhead between physics and UI without compromising thread safety.

Investigate:

- snapshot construction frequency;
- snapshot size;
- unnecessary body metadata copying;
- redundant diagnostics snapshotting;
- UI polling frequency;
- signal/slot traffic.

### Possible improvements

- publish snapshots at a controlled UI/render cadence while physics continues independently;
- avoid rebuilding unchanged metadata;
- reduce duplicate conversion between NumPy and Python structures;
- coalesce redundant UI updates.

Do not make the renderer access mutable `SolarSystem` state.

---

# 8. Workstream 5 — Rendering/OpenGL optimization

## Objective

Improve rendering performance independently from physics performance.

## 8.1 Uniform caching

Cache OpenGL uniform locations instead of repeatedly looking them up during rendering.

## 8.2 Buffer management

Profile:

- vertex buffer updates;
- trail uploads;
- body-instance data;
- text/label rendering.

Only optimize measured hotspots.

## 8.3 Trail rendering

Measure trail cost as body count and trail length increase.

Potential improvements:

- bounded trail buffers;
- incremental updates;
- reduced upload frequency;
- configurable history length.

Do not silently change visual behavior.

## 8.4 Camera/reference-body path

Ensure camera calculations do not introduce unnecessary copies or conversions.

### Acceptance criteria

A rendering benchmark must demonstrate measurable improvement in the targeted
scenario without changing physical state.

---

# 9. Workstream 6 — Horizons/data-loading optimization

## Objective

Make external data loading faster and more robust without changing returned physical data.

## 9.1 Cache efficiency

Measure:

- cache hit time;
- cache miss time;
- parsing time;
- disk I/O.

## 9.2 Request scheduling

Investigate bounded concurrency for independent Horizons requests.

Rules:

- bounded concurrency only;
- respect service limits;
- no uncontrolled request fan-out;
- deterministic assembly of returned bodies;
- failures must remain transactional.

## 9.3 Cache validation

Preserve the existing cache semantics.

A failed or incomplete request must not corrupt valid cached data.

### Acceptance criteria

- measurable improvement for multi-body loads;
- no increase in failed loads;
- deterministic body ordering;
- existing transactional loading tests remain green.

---

# 10. Workstream 7 — Scalability benchmarks

## Objective

Move beyond the fixed 39-body Solar System benchmark.

Create synthetic benchmark families, for example:

- N = 2
- N = 10
- N = 39
- N = 100
- N = 250
- N = 500
- N = 1000

The exact upper limit should be determined experimentally.

### Measure

For each N:

- wall-clock time;
- physics steps/second;
- simulated days/second;
- substeps/second;
- memory usage;
- diagnostics overhead;
- snapshot overhead.

### Important distinction

Separate:

1. physics-only performance;
2. physics + diagnostics;
3. physics + diagnostics + snapshots;
4. complete interactive application.

This tells us where the scaling cost actually originates.

### Output

Produce a reproducible benchmark table and, where useful, plots.

# 11. Workstream 8 — Diagnostics UI usability and performance

The following v0.7 items belong naturally here.

## 11.1 Drift badges

Add clear color-coded indicators for:

- energy drift;
- linear momentum drift;
- angular momentum drift;
- optionally center-of-mass drift.

### Requirements

Thresholds must be explicit and documented.

Suggested conceptual states:

- green: within expected numerical tolerance;
- amber: elevated but not immediately problematic;
- red: outside expected tolerance.

Do not hard-code scientifically arbitrary thresholds without documenting their basis.

Prefer configurable constants in one location.

## 11.2 Time-window selector

Add a selector for:

- recent history / e.g. last 100 simulated days;
- recent long history / e.g. last 1 year;
- all retained history.

The selector should operate on the existing bounded history buffer.

Do not introduce unbounded history merely to support the selector.

## 11.3 Plot decimation

If profiling demonstrates that large histories cause redraw cost, decimate data
for display while retaining the original numerical history for export.

Never alter exported scientific data merely for visualization.

## 11.4 Diagnostics refresh throttling

The UI should not redraw faster than necessary.

Physics and diagnostics collection should remain independent from plot refresh.

### Acceptance criteria

- UI remains responsive;
- diagnostics do not materially reduce physics throughput;
- scientific values are unchanged;
- plot/export data remain distinguishable.

# 12. Workstream 9 — Performance regression tests

Performance tests must avoid brittle absolute timing assertions.

Prefer:

- benchmark result recording;
- baseline comparison;
- broad regression thresholds;
- deterministic workload definitions.

Example:

```text
benchmark_name
body_count
dt
iterations
physics_time
wall_time
throughput
memory_peak
```

Avoid tests such as:

```text
assert runtime < 0.100 seconds
```

unless the environment is controlled.

### Recommended regression policy

A performance regression should be flagged when a stable benchmark changes by a
meaningful percentage relative to the recorded baseline.

The exact threshold should be established after collecting multiple baseline runs.

# 14. What v0.8 should NOT do

Do not introduce these simply because they might improve performance:

- GPU acceleration;
- CUDA;
- OpenCL;
- Barnes-Hut;
- Fast Multipole Methods;
- distributed simulation;
- multiprocessing architecture;
- a complete physics-engine rewrite.

These remain possible future directions, but should only be considered after the
v0.8 measurements demonstrate that the current architecture is insufficient.

A measured conclusion such as:

> "The vectorized O(N²) kernel remains adequate through N=500"

is a successful v0.8 result.

# 15. Numerical correctness gates

Every optimization must preserve:

- total energy calculation;
- momentum;
- angular momentum;
- center of mass;
- orbital elements;
- deterministic benchmarks;
- convergence behavior;
- collision outcomes;
- numerical-failure handling.

At minimum, after each significant optimization:

```text
pytest
benchmark suite
validation suite
```

For physics-kernel changes, compare the optimized result against the existing
reference implementation for deterministic states.

# 18. PR decision rule

Create the PR only if:

- all numerical validation remains green;
- the performance work is supported by measurements;
- no known correctness regression exists;
- benchmark results are reproducible enough to explain;
- diagnostics remain scientifically correct;
- the full test suite passes;
- documentation matches the actual implementation.

Do not hold the PR because a hypothetical GPU/Barnes-Hut solution would be faster.
If measurements show the current O(N²) engine is adequate for the project's target
scale, that is a valid and desirable v0.8 outcome.
