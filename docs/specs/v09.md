# NBodiesGravity v0.9 — Advanced Simulation Capabilities & Pre-v1.0 Hardening

**Branch:** `v09`  
**Base:** `v08` after final PR-readiness items are completed  
**Target:** `main`  
**Theme:** Advanced simulation capabilities, integrator extensibility, reproducibility, experiment workflows, and scientific hardening  
**Status:** Detailed implementation plan

---

# 1. Executive Summary

Version 0.9 is the final major feature release before v1.0.

The purpose of v0.9 is **not** to replace the existing numerical engine or introduce a large collection of experimental physics models. The goal is to turn the validated v0.8 engine into a more general scientific simulation framework while preserving the v0.8 implementation as the reference baseline.

The central v0.9 idea is:

> **Keep the validated Newtonian + Velocity Verlet engine as the trusted baseline, while introducing explicit extension points for alternative integrators, initial-condition presets, reproducible experiments, and controlled physical-model variations.**

The release should therefore make a clear distinction between:

1. **Validated baseline behaviour**
   - Newtonian point-mass gravity
   - Plummer softening
   - Velocity Verlet
   - adaptive timestep controller
   - collision/merger model
   - SSB/reference-frame support
   - v0.8 numerical validation

2. **Alternative/experimental behaviour**
   - additional integrators
   - different timestep strategies
   - alternative collision models
   - specialized initial conditions
   - experiment-specific configurations

A user must always be able to identify which model and numerical method produced a result.

# 2. v0.9 Goals

## Primary goals

- [ ] Introduce a clean pluggable integrator architecture.
- [ ] Preserve the current Velocity Verlet implementation as the default/reference integrator.
- [ ] Implement at least one alternative integrator, preferably Leapfrog / Störmer-Verlet.
- [ ] Provide deterministic initial-condition presets.
- [ ] Provide reproducible simulation checkpoints.
- [ ] Add experiment metadata and configuration capture.
- [ ] Add explicit integration limits and controlled stepping.
- [ ] Make physical-model choices explicit/configurable.
- [ ] Formalize collision/merger model extensibility.
- [ ] Build cross-integrator scientific validation.
- [ ] Improve UI support for selecting and inspecting simulation models.
- [ ] Improve reproducibility and deterministic replay.
- [ ] Harden the system for v1.0.
- [ ] Keep v0.9 backward-compatible with existing saved systems where practical.

---

# 3. Non-Goals

The following should **not** become v0.9 requirements unless measurements or scientific requirements make them unavoidable:

- GPU/N-body CUDA implementation.
- Barnes-Hut or tree-based gravity.
- Fast multipole methods.
- Multiprocessing-based force calculation.
- Distributed simulation.
- Relativistic gravity.
- Full collision physics / hydrodynamics.
- Planetary atmosphere modelling.
- Tidal deformation.
- N-body chaos prediction.
- Arbitrary user scripting inside the simulation.
- A complete plugin marketplace/framework.
- High-order integrators beyond what is needed for the architecture and validation.
- Rewriting the existing rendering architecture.
- Replacing NumPy with another numerical backend.

These may be future projects, but they should not destabilize the v1.0 baseline.

# 4. Scientific Design Principle

## 4.1 One trusted baseline

The existing v0.8 engine remains the reference implementation.

The default configuration should continue to be equivalent to:

```text
Newtonian gravity
+
Plummer softening
+
Velocity Verlet
+
adaptive timestep controller
+
existing collision/merger behaviour
+
existing SSB/reference-frame model
```

No v0.9 architecture change should silently alter this behaviour.

---

## 4.2 Explicit model identification

Every simulation should be able to answer:

- Which integrator was used?
- Which timestep policy was used?
- Which gravitational model was used?
- Which softening value was used?
- Which collision model was used?
- Which initial-condition preset was used?
- Which epoch was used?
- Which units were used?
- Which reference frame was used?
- Which application version generated the result?

This metadata becomes essential for reproducibility.

# 5. Workstream 1 — Integrator Abstraction

## Objective

Separate the simulation system from the concrete numerical integration algorithm.

The current `SolarSystem` should not need to know implementation details of Velocity Verlet.

Instead, it should depend on a stable integrator interface.

---

## 5.1 Define integrator interface

Create a clear abstraction around the numerical step.

Possible conceptual API:

```python
class Integrator(ABC):
    @abstractmethod
    def step(
        self,
        positions,
        velocities,
        masses,
        dt,
        *,
        accelerations=None,
    ):
        ...
```

The exact signature should be adapted to the existing engine rather than blindly replacing the current API.

The interface should expose enough information for:

- positions;
- velocities;
- accelerations;
- timestep;
- numerical diagnostics;
- optional integrator state.

---

## 5.2 Integrator configuration

Create an explicit configuration object.

Conceptually:

```python
@dataclass
class IntegratorConfig:
    name: str
    parameters: ...
```

Avoid putting integrator-specific settings into `SolarSystem`.

For example:

```text
TimeStepConfig
IntegratorConfig
PhysicsConfig
CollisionConfig
```

should remain conceptually separate.

---

## 5.3 Velocity Verlet adapter

Refactor the current implementation into the new interface without changing its mathematics.

Acceptance criteria:

- default simulation produces equivalent numerical results;
- existing tests continue to pass;
- v0.8 benchmark characteristics do not regress materially;
- acceleration reuse remains supported;
- adaptive timestep remains outside the integrator if that is the cleaner architectural boundary.

---

## 5.4 Integrator state

Determine whether each integrator requires persistent state.

Velocity Verlet is effectively stateless between steps except for optional cached acceleration.

Future integrators may require:

- previous acceleration;
- previous position;
- predictor/corrector state;
- multi-step history.

Therefore the interface must allow optional internal state without forcing state into `SolarSystem`.

---

# 6. Workstream 2 — Leapfrog / Störmer-Verlet

## Objective

Implement one alternative integrator to validate the new architecture.

Leapfrog is the recommended first candidate because it is:

- simple;
- closely related to Velocity Verlet;
- second-order;
- well suited to Hamiltonian gravitational systems;
- useful for scientific cross-validation.

---

## 6.1 Implementation

Implement a clearly named integrator such as:

```text
LeapfrogIntegrator
```

Use a kick-drift-kick or equivalent mathematically consistent formulation.

Document the exact variant.

---

## 6.2 Fixed timestep first

The first Leapfrog implementation should support fixed `dt`.

Do not immediately combine it with every adaptive-timestep feature.

This makes validation substantially easier.

---

## 6.3 Adaptive timestep compatibility

After fixed-dt validation, determine whether the common adaptive timestep controller can safely be used with Leapfrog.

Important:

The documentation must not describe adaptive Leapfrog as formally symplectic if variable timestep changes destroy that property.

Use careful wording such as:

> “Second-order Leapfrog integration with adaptive timestep control.”

if adaptive mode is supported.

---

## 6.4 Cross-validation

Compare Velocity Verlet and Leapfrog using:

- two-body circular orbit;
- eccentric orbit;
- Earth-Sun-like system;
- Earth-Moon-like system;
- long-term orbital stability.

Measure:

- energy drift;
- angular momentum drift;
- linear momentum;
- COM;
- orbital-element drift;
- phase error;
- position error against reference trajectories.

---

# 8. Workstream 4 — Initial-Condition Presets

## Objective

Make scientifically meaningful test scenarios easy to reproduce.

Presets should be data/configuration driven rather than hard-coded into the UI.

---

## 8.1 Circular two-body

Parameters:

- primary mass;
- secondary mass;
- separation;
- orbital plane;
- epoch;
- reference frame.

Expected result:

- approximately circular orbit;
- stable semi-major axis;
- low eccentricity;
- predictable period.

---

## 8.2 Eccentric two-body

Parameters:

- primary mass;
- secondary mass;
- semi-major axis;
- eccentricity;
- orientation;
- true anomaly.

This validates:

- periapsis;
- apoapsis;
- orbital period;
- eccentricity preservation.

---

## 8.3 Oriented two-body

Support configurable:

- inclination;
- longitude of ascending node;
- argument of periapsis;
- true anomaly.

This directly validates the orbital-elements implementation from v0.7.

---

## 8.4 Earth-Moon preset

Create a deterministic Earth-Moon-like system suitable for:

- integrator comparison;
- timestep experiments;
- conservation validation;
- collision testing.

The exact parameters should be stored explicitly rather than embedded as unexplained constants.

---

## 8.5 Binary-star preset

Two comparable masses orbiting their common barycenter.

Useful for:

- COM validation;
- momentum validation;
- symmetric-force validation;
- reference-frame testing.

---

## 8.6 Restricted three-body preset

Optional but strongly recommended.

Example:

- two massive primaries;
- negligible-mass test particle.

Useful for:

- orbital dynamics;
- Lagrange-point experiments;
- integrator comparison.

The test particle should still be represented consistently by the engine.

---

## 8.7 Custom preset

Allow users/tests to create a scenario programmatically from explicit:

```text
positions
velocities
masses
labels
epoch
configuration
```

This becomes the foundation for reproducible scientific tests.

# 10. Workstream 6 — Reproducibility & Checkpoints

## Objective

Allow a simulation to be saved at a precise point and resumed.

Existing save/load functionality stores the system configuration. v0.9 should distinguish:

### Initial configuration

What the simulation started from.

### Checkpoint

The exact state at a simulation time.

---

## 10.1 Checkpoint contents

A checkpoint should contain:

- positions;
- velocities;
- masses;
- body metadata;
- simulation epoch;
- elapsed simulation time;
- timestep configuration;
- integrator;
- physics configuration;
- collision configuration;
- reference-frame configuration;
- application/schema version;
- experiment metadata;
- any required integrator state.

---

## 10.2 Deterministic resume

Loading a checkpoint and continuing should reproduce the same trajectory as uninterrupted execution within the documented numerical tolerance.

Test:

```text
Run A:
  integrate 1000 steps continuously

Run B:
  integrate 500 steps
  save checkpoint
  reload
  integrate 500 steps
```

Compare:

- positions;
- velocities;
- time;
- diagnostics.

---

## 10.3 Checkpoint schema version

Introduce explicit schema versioning.

Do not rely solely on application version.

Example:

```text
format_version
checkpoint_version
application_version
```

---

# 17. Workstream 13 — Scientific Validation Suite

This is one of the most important v0.9 workstreams.

The goal is not merely to prove that the new features run. The goal is to prove that they produce scientifically sensible results.

---

## 17.1 Integrator equivalence tests

For identical initial conditions and fixed timestep:

- Velocity Verlet;
- Leapfrog.

Compare trajectories.

Expected:

- both are second-order;
- differences decrease approximately quadratically with timestep in appropriate regimes.

---

## 17.2 Two-body analytical tests

Use known Keplerian solutions.

Validate:

- semi-major axis;
- eccentricity;
- period;
- periapsis;
- apoapsis;
- orbital orientation.

---

## 17.3 Conservation tests

For closed systems validate:

- total energy;
- linear momentum;
- angular momentum;
- center of mass.

Test across:

- integrators;
- timestep sizes;
- representative scenarios.

---

## 17.4 Convergence tests

For each integrator:

```text
dt
dt/2
dt/4
```

Measure error against:

- analytical solution;
- high-resolution reference solution.

Verify expected order where applicable.

Do not overstate exact order when adaptive timesteps are involved.

---

## 17.5 Long-term stability

Run representative long simulations.

Measure:

- energy drift;
- orbital-element drift;
- COM drift;
- angular momentum drift.

Compare integrators rather than defining a universal “good” threshold without scientific justification.

---

# 18. Workstream 14 — Reproducibility Tests

Create tests for:

### Same inputs

Same initial state and configuration → same result.

### Save/load

Save and reload initial conditions → same result.

### Checkpoint/resume

Continuous run vs checkpointed run → same result within tolerance.

### Replay

Serialized experiment → regenerated experiment produces same result.

### Version metadata

Saved experiment identifies the software/schema version.

# 19. Workstream 15 — Backward Compatibility

Existing v0.5–v0.8 save files should continue to load where practical.

The loader should provide defaults for newly introduced fields.

For example, an old save without integrator metadata should resolve to:

```text

```

An old save without explicit collision configuration should resolve to the current merge model.

## 19.1 Never silently reinterpret old physics

Backward compatibility must not mean changing historical model semantics.

If an old file cannot be faithfully interpreted, fail clearly rather than silently changing its meaning.

# 29. Scientific Validation Protocol

For reproducibility, record a standard validation configuration.

Example:

```text
Scenario:
    circular two-body
```

# 30. Convergence Interpretation

For a second-order method, error should approximately scale as:

```text
E(dt) ∝ dt²
```

Therefore halving `dt` should reduce the dominant discretization error by approximately a factor of four in a suitable fixed-timestep experiment.

Do not demand exactly 4×.

Floating-point error, softening, finite reference accuracy, and implementation details can alter the observed ratio.

For adaptive timestep experiments, report observed behaviour rather than claiming formal fixed-step order.

# 33. Performance Acceptance Criteria

The exact numerical thresholds should be based on the measured v0.8 baseline.

Required principles:

1. Velocity Verlet must not suffer a material regression merely because of abstraction.
2. The default 39-body Solar System must remain responsive.
3. Leapfrog performance should be characterized.
4. Presets should have negligible runtime overhead after initialization.
5. Checkpoint serialization must not block the physics loop unexpectedly.
6. UI configuration must not introduce per-step overhead.

Avoid imposing fragile machine-specific steps/sec requirements in ordinary unit tests.

- stable field names;
- units documented;
- backwards-compatible defaults where possible.

Use JSON-compatible primitive structures.

For arrays, preserve:

- dtype expectations where important;
- shape;
- units;

# 35. Numerical Failure Policy

v0.6 introduced numerical-integrity checks.

v0.9 should preserve and extend this policy.

On detection of:

- NaN;
- Inf;
- impossible timestep;
- invalid state;

the engine should:

1. stop or reject the invalid operation;
2. log a useful diagnostic;
3. preserve the last valid state where possible;
4. avoid writing a corrupt checkpoint;
5. expose the failure to the caller/UI.

Do not allow an invalid state to propagate silently.

---

# 36. Threading Requirements

The simulation thread should remain responsible for:

- physics;
- checkpoint generation when appropriate;
- snapshot publication.

The UI should not mutate simulation state directly.

Potentially expensive operations such as:

- checkpoint serialization;
- large experiment export;

should be evaluated for asynchronous handling if profiling shows UI impact.

Do not add threading complexity without evidence of a problem.

---

# 37. Rendering Requirements

v0.9 should consume the same immutable snapshot model established in v0.8.

Do not introduce renderer access to integrator internals.

If simulation metadata is displayed, publish it through an appropriate immutable state/configuration interface.

The renderer should remain decoupled from numerical implementation details.

The most important decision for v0.9 is:

# 45. v0.9 vs v1.0 Boundary

v0.9 should answer:

> “Can NBodiesGravity support more than one numerical method and reproducible scientific experiments without compromising the validated baseline?”

v1.0 should answer:

> “Is the resulting simulator stable, documented, scientifically validated, reproducible, and reliable enough to call the architecture and default behaviour a stable release?”

Therefore v0.9 is allowed to contain clearly marked experimental capabilities.

v1.0 should be much more conservative.

# 46. Final Recommendation

The implementation should proceed in this order:

**Integrator abstraction → Velocity Verlet preservation → Leapfrog → scientific validation → presets → reproducibility/checkpoints → explicit physical configuration → controlled stepping → UI integration → compatibility → performance validation → documentation → PR.**

The most important rule is:

> **Never trade away the validated v0.8 baseline in order to make v0.9 more flexible.**

If an architectural refactor makes the baseline numerically or materially slower, stop and resolve that regression before adding more v0.9 functionality.

At the end of v0.9, the project should have:

- one trusted default integrator;
- one scientifically useful alternative;
- reproducible initial conditions;
- reproducible checkpoints;
- explicit simulation metadata;
- controlled experiment execution;
- cross-integrator scientific validation;
- a cleaner foundation for future integrators and physics models;
- no loss of the v0.8 performance/correctness baseline.

**Recommended v0.9 philosophy: extend the simulator, do not destabilize it.**
