# NBodiesGravity v0.9.0 — Detailed Implementation Plan

## 1. Release objective

**v0.9.0 is the advanced simulation capabilities and pre-v1.0 hardening release.**

The objective is to turn the validated v0.8 simulation engine into a more flexible
scientific experiment platform while keeping the existing validated baseline clearly
defined.

v0.9 should introduce:

- pluggable integration methods;
- reusable scientifically defined initial-condition presets;
- deterministic checkpoints/replay;
- improved simulation controls;
- configurable physical models where justified;
- stronger experiment/reproducibility infrastructure.

The central rule is:

> **Experimental capabilities must be selectable, reproducible, testable, and clearly separated from the validated default model.**

Unlike v0.8, a significant part of v0.9 can already be specified in detail today because
the roadmap, v0.6 numerical infrastructure, and v0.7 diagnostics establish the required
interfaces and scientific validation approach.

However, v0.9 should remain conditional on the actual v0.8 results. In particular,
performance findings from v0.8 may change which integration options or checkpoint
mechanisms deserve priority.

---

# 2. Baseline

v0.9 assumes v0.8 has delivered:

- measured physics performance;
- measured scalability envelope;
- stable simulation-thread architecture;
- diagnostics UI;
- bounded diagnostics history;
- scientific exports;
- deterministic benchmark suite;
- numerical validation suite;
- performance regression benchmarks;
- optimized but validated O(N²) baseline;
- documented rendering/data-loading performance;
- drift badges;
- diagnostics time-window controls.

The default physical model remains:

```text
Newtonian gravity
+
Plummer softening
+
Velocity Verlet
+
adaptive timestep
+
collision merging
```

That combination remains the **validated baseline**.

# 4. Workstream 1 — Pluggable integrator architecture

## Objective

Separate the concept of "how the equations are integrated" from `SolarSystem`.

The current engine should evolve from:

```text
SolarSystem
    |
    +--> fixed Velocity Verlet implementation
```

toward:

```text
SolarSystem
    |
    +--> Integrator interface
             |
             +--> Velocity Verlet
             +--> Leapfrog
             +--> future integrators
```

The existing behavior must remain the default.

## 4.1 Integrator interface

Conceptually:

```python
class Integrator(Protocol):
    def step(
        self,
        state,
        dt,
        acceleration_fn,
    ) -> new_state:
        ...
```

The exact API should follow the project's existing architecture and ownership rules.

The integrator must not own:

- UI state;
- rendering state;
- persistence;
- diagnostics history;
- camera state.

It should operate on physical state and return validated physical state.

## 4.2 Integration configuration

Introduce an explicit configuration object, conceptually:

```text
IntegratorConfig
    method
    fixed/adaptive policy
    tolerances where applicable
    method-specific parameters
```

Do not duplicate timestep configuration unnecessarily.

`TimeStepConfig` remains responsible for timestep selection/budgeting;
the integrator is responsible for applying a selected timestep.

# 5. Workstream 2 — Additional integrators

## 5.1 Leapfrog / kick-drift-kick

The first additional method should be a closely related second-order method.

Reasons:

- scientifically well understood;
- useful comparison against Velocity Verlet;
- relatively small implementation risk;
- useful for long-term Hamiltonian behavior experiments.

Implement one clearly defined variant rather than many superficially different schemes.

## 5.2 Higher-order integrator

A higher-order method may be added only if there is a demonstrated use case.

Candidates can include:

- RK4;
- another well-established method appropriate to the project.

Do not add it merely because it is familiar.

The choice should be justified using v0.8/v0.9 benchmark evidence.

## 5.3 Adaptive timestep compatibility

Every integrator must explicitly document whether it supports:

- fixed timestep;
- adaptive timestep;
- collision merging;
- numerical failure detection.

Do not assume that a method's fixed-step properties automatically carry over to
the current adaptive-step controller.

# 6. Workstream 3 — Initial-condition presets

## Objective

Make scientifically defined systems reproducible without manually editing individual
bodies.

Required first presets:

### 6.1 Two-body circular orbit

Parameters:

- primary mass;
- secondary mass;
- orbital radius;
- orbital plane orientation;
- phase.

Generate velocity analytically.

### 6.2 Two-body eccentric orbit

Parameters:

- primary mass;
- secondary mass;
- semi-major axis;
- eccentricity;
- inclination;
- Ω;
- ω;
- ν.

Use the same orbital-element conventions as v0.7.

### 6.3 Earth-Moon

A deterministic benchmark/visualization preset.

### 6.4 Binary system

Configurable masses and orbital elements.

### 6.5 Restricted three-body configuration

Provide a reproducible configuration suitable for studying:

- libration;
- stability;
- Lagrange points.

### 6.6 Custom planetary system

Allow users to specify a star plus generated planets from orbital parameters.

# 7. Preset architecture

Presets should be data-driven rather than hard-coded UI callbacks.

Conceptually:

```text
PresetDefinition
    name
    description
    parameters
    build_system()
```

A preset should produce a complete physical initial state.

Every preset should include:

- deterministic parameters;
- reference epoch/time;
- expected qualitative behavior;
- optional analytical reference values.

---

# 8. Workstream 4 — Deterministic checkpoints

## Objective

Allow users to save the complete physical simulation state at a point in time and
resume it exactly within the supported reproducibility envelope.

## 8.1 Checkpoint contents

At minimum:

- simulation elapsed time;
- simulation epoch;
- body identities;
- body labels/configuration;
- positions;
- velocities;
- masses;
- radii;
- active state;
- trail configuration if considered UI state;
- integrator type;
- timestep configuration;
- adaptive timestep state if relevant;
- physical-model configuration;
- random-generator state if randomness is introduced;
- checkpoint format version.

## 8.2 Distinguish save vs checkpoint

Existing JSON save/load represents a user-editable system configuration.

A checkpoint is different:

> a restartable numerical state.

Do not silently overload the existing save format if doing so would make it ambiguous.

Use explicit checkpoint versioning.

---

# 9. Checkpoint atomicity

Checkpoint creation must be transactional.

The checkpoint must represent one coherent physical state.

Avoid:

```text
body 1 copied
body 2 copied
simulation advances
body 3 copied
```

Instead, checkpoint from a consistent immutable snapshot or equivalent state boundary.

## Acceptance criteria

- save checkpoint does not mutate simulation state;
- loading a checkpoint restores the same physical state;
- failed checkpoint loading leaves current simulation unchanged;
- incompatible checkpoint versions fail clearly.

---

# 10. Workstream 5 — Replay and reproducibility

## Objective

Allow an experiment to be reproduced from a defined initial state and configuration.

A replay record should identify:

- initial state/preset;
- epoch;
- integrator;
- timestep configuration;
- physical model;
- software version;
- checkpoint/restart points;
- simulation duration;
- relevant random seed/state.

## Important limitation

Do not promise bit-for-bit reproducibility across:

- different CPUs;
- different NumPy versions;
- different BLAS implementations;
- different Python versions

unless experimentally demonstrated.

Define two levels:

### Level 1 — deterministic configuration

Same inputs and configuration.

### Level 2 — numerical reproducibility

Same environment and supported software stack.

Document what is guaranteed.

---

# 11. Workstream 6 — Advanced simulation controls

Add scientific controls that make experiments easier to perform.

## 11.1 Single-step forward

Allow one integration update at a time.

The UI should clearly distinguish:

- one simulation step;
- one adaptive substep;
- one configured time increment.

Prefer one unambiguous user-facing operation.

## 11.2 Configurable integration limits

Allow users to specify:

- simulation end time;
- maximum wall-clock execution time;
- optional maximum number of integration steps/substeps.

The existing computational-budget safety model remains authoritative.

## 11.3 Pause/resume

Preserve current semantics but ensure checkpoints and single-step execution interact
cleanly with pause/resume.

## 11.4 Restart

Restart should restore the exact defined initial state, not merely reconstruct it
approximately.

## 11.5 Rewind

Rewind should operate through checkpoints.

Do not attempt arbitrary reverse integration unless a future release establishes that
the selected integrators and physical models support it reliably.

# 12. Workstream 7 — Configurable physical models

## Objective

Make model assumptions explicit and selectable without contaminating the validated
default.

Potential configurable components:

```text
GravityModel
SofteningModel
CollisionModel
```

The default configuration remains the current validated model.

---

# 13. Configurable softening

Allow:

- current default epsilon;
- user-configured epsilon;
- optionally epsilon = 0 for a carefully controlled experimental mode.

The UI/documentation must make clear that changing epsilon changes the physical
numerical model.

Scientific diagnostics should record the selected epsilon.

Validation tests should verify:

- default behavior unchanged;
- acceleration scaling;
- close-encounter behavior;
- energy definition remains consistent with selected force/potential model.

---

# 14. Workstream 8 — Collision/merger model framework

The current collision merging behavior should become an explicit model.

Potential initial choices:

### Model A — Merge

Current validated behavior:

- mass conserved;
- linear momentum conserved;
- center-of-mass position;
- merged radius according to documented rule.

### Model B — No merge

Bodies may pass through or collision can be reported without merging.

This is primarily useful for controlled experiments.

### Future experimental models

Possible later additions:

- fragmentation;
- inelastic collision with configurable restitution;
- impact-energy reporting.

Do not implement fragmentation unless there is a clear scientific requirement.

---

# 15. Collision-model validation

For every collision model:

- mass conservation;
- momentum behavior;
- energy behavior;
- radius behavior;
- body-count transition;
- deterministic outcome.

The diagnostics layer must make model changes visible.

Do not compare energy conservation between two different collision models as if they
were expected to have the same behavior.

# 17. Workstream 10 — Validation and cross-integrator comparison

This is one of the most important v0.9 workstreams.

Every new integrator must be tested against the existing benchmark suite.

## 17.1 Canonical benchmarks

At minimum:

- free particle;
- circular two-body;
- eccentric two-body;
- Earth-Sun;
- Earth-Moon;
- Lagrange three-body.

## 17.2 Metrics

Measure:

- energy drift;
- momentum drift;
- angular momentum drift;
- orbital-element drift;
- phase error;
- position error;
- runtime;
- number of substeps;
- stability duration.

## 17.3 Fixed timestep

Compare methods at equivalent fixed timesteps.

## 17.4 Adaptive timestep

Compare only where the method's adaptive semantics are scientifically justified.

Do not claim a generic "best integrator."

The goal is to expose trade-offs.

# 18. Analytical validation for generated presets

Every analytically generated two-body preset should have known expected values.

For example:

```text
input:
a
e
i
Ω
ω
ν

expected:
orbital elements recovered within tolerance
```

This directly connects the v0.7 orbital-elements implementation with the v0.9
initial-condition generator.

A generated state should round-trip:

```text
orbital elements
      ↓
Cartesian state
      ↓
orbital element calculation
      ↓
original elements
```

within defined numerical tolerances.

This should become a high-value regression suite.

# 21. What should remain outside v0.9

Do not allow v0.9 to become an unlimited physics-research release.

Explicitly defer unless justified:

- full general relativity;
- relativistic N-body solver;
- arbitrary high-order symplectic integrator library;
- SPH/fluid simulation;
- gas dynamics;
- planetary atmospheres;
- stellar evolution;
- GPU rewrite;
- distributed simulation;
- automatic scientific parameter optimization;
- machine-learning-based integration.

Optional relativistic corrections are acceptable only as a small, clearly experimental
model if the project goals still support them.

# 24. v0.9 release gates

Do not create the PR if any of these fail:

### Numerical

- default integrator behavior regresses;
- conservation tests regress;
- benchmark stability regresses unexpectedly;
- generated analytical orbits do not round-trip;
- checkpoint restart changes the physical state beyond defined tolerances.

### Reproducibility

- checkpoint metadata is incomplete;
- software/configuration identity cannot be recovered;
- deterministic presets produce different initial states unexpectedly.

### Persistence

- old v0.5/v0.6/v0.7 saves stop loading without a justified migration;
- checkpoint corruption can silently produce a valid-looking but incorrect simulation.

### Architecture

- integrator-specific logic leaks into unrelated UI/rendering code;
- experimental physics changes the validated default;
- mutable state crosses the simulation/rendering boundary unsafely.

# 26. Is v0.9 detailed enough to plan now?

**Yes — substantially.**

The major architecture and feature families are foreseeable now because they follow
directly from the existing roadmap:

- additional integrators;
- initial-condition presets;
- checkpoints/replay;
- advanced simulation controls;
- more advanced collision/physical models.

The exact implementation details should still be allowed to change after v0.8.

In particular, v0.8 profiling may change:

- which integrator is most useful;
- whether a higher-order method is necessary;
- checkpoint frequency limits;
- how large preset systems should be;
- whether certain performance optimizations are worth keeping.

Therefore this document should be treated as a **detailed architectural plan**, not a
promise that every listed experimental feature must ship.
