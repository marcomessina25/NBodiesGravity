# 1. Executive Summary

Version 1.0 is **not another major feature release**.

By the end of v0.9, the project has:

- a real-time N-body engine;
- validated Newtonian gravity;
- adaptive timestep control;
- collision/merger handling;
- scientific diagnostics;
- orbital-element analysis;
- performance/scalability infrastructure;
- pluggable integrators;
- Leapfrog;
- deterministic presets;
- checkpoints;
- experiment metadata;
- replay/reproducibility;
- explicit physical configuration.

The purpose of v1.0 is therefore:

> **Freeze the scientifically validated baseline, remove remaining ambiguity, harden the application, document its guarantees and limitations, and make the simulator reliable enough to call the architecture and default behaviour a stable release.**

No major new physics should be required for v1.0.

---

# 2. v1.0 Release Philosophy

The project should distinguish three categories.

## Stable baseline

```text
Newtonian point-mass gravity
+
Plummer softening
+
Velocity Verlet
+
adaptive timestep control
+
existing collision/merger model
+
SSB/reference-frame support
```

This is the configuration whose behaviour v1.0 promises to maintain.

## Supported alternative

```text
Leapfrog / Störmer-Verlet
```

Supported and scientifically validated, but not necessarily the default.

## Experimental/future

Anything not covered by the v1.0 validation matrix should not be presented as equally validated.

# 6. Workstream 2 — Scientific Guarantees and Limitations

Create a concise user-facing section:

```text
What v1.0 guarantees
What v1.0 does not guarantee
```

Document, for example:

### Guarantees

- deterministic results for identical inputs within the documented environment/tolerance;
- conservation properties within documented numerical error;
- supported backward-compatible save loading;
- stable default numerical configuration.

### Limitations

- adaptive timestep is not formally fixed-step symplectic integration;
- finite floating-point precision;
- Plummer softening changes the exact short-range Newtonian potential;
- collision merging is a model choice, not detailed impact physics;
- chaotic systems can diverge from another valid numerical implementation;
- N-body force calculation remains O(N²).

# 14. Workstream 10 — Numerical Failure UX

# 29. Definition of v1.0

The project should only call itself v1.0 when this statement is defensible:

> **NBodiesGravity provides a stable, documented and reproducible Newtonian N-body simulation environment with a validated Velocity Verlet baseline, an independently validated Leapfrog alternative, deterministic initial-condition presets, checkpoint/replay support, numerical diagnostics, backward-compatible persistence, and known performance/scientific limitations.**

This does **not** mean:

> “NBodiesGravity perfectly reproduces the real Solar System.”

The simulator remains a numerical model with:

- finite precision;
- softening;
- finite timestep;
- simplified collision physics;
- O(N²) gravity;
- chaotic long-term dynamics.

Those limitations should be explicit in the v1.0 documentation.

# 30. Final Decision Rule

v1.0 may be released only if:

### Scientific correctness
- all mandatory validation tests pass;
- no unexplained regression exists;
- default behaviour is frozen.

### Reproducibility
- checkpoint/replay passes;
- reproducibility scope is documented;
- configuration provenance is complete.

### Compatibility
- supported historical saves load correctly;
- schema behaviour is documented.

### Performance
- baseline is recorded;
- no material unexplained regression exists;
- memory/resource behaviour is acceptable.

### Application stability
- thread lifecycle is clean;
- numerical failures are contained;
- UI workflows are reliable;
- external-data failures are handled.

### Documentation
- user-facing documentation matches implementation;
- scientific limitations are explicit.

### Release engineering
- clean environment works;
- CI is green;
- RC passes;
- final release diff is clean.

# 32. Final Philosophy

The project progression is:

```text
v0.5  State/application correctness
  ↓
v0.6  Numerical robustness
  ↓
v0.7  Scientific diagnostics
  ↓
v0.8  Performance/scalability
  ↓
v0.9  Extensibility + reproducibility
  ↓
v1.0  Stability + validation + release
```

The purpose of v1.0 is not to make NBodiesGravity capable of everything.

It is to make the capabilities already implemented **trustworthy, reproducible, documented, and stable enough to constitute a real 1.0 release.**

**Recommended v1.0 philosophy: freeze, validate, harden, document, release.**
